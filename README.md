# Классификация рекламных креативов

Сервис для автоматического анализа и тематической классификации рекламных
изображений. По загруженной картинке пайплайн извлекает текст (OCR), находит
объекты (YOLOv8), выделяет доминирующие цвета, считает визуальный эмбеддинг
(CLIP) и на основании всего этого предсказывает тематику креатива из 20
категорий (помады, парфюм, обувь, сумки и т.д.). Все тяжёлые модели работают
на CPU, GPU не требуется.

Проект сделан как дипломная работа, поэтому изначально рассчитан на простое
локальное развёртывание через docker-compose.

## Стек

- **Backend:** FastAPI, SQLAlchemy, Alembic
- **Очередь:** Celery + Redis
- **Хранилище:** PostgreSQL (метаданные), MinIO (исходные изображения и веса
  моделей), S3-совместимый
- **ML:** BERT (bert-base-multilingual-cased), CLIP (openai/clip-vit-base-patch32),
  YOLOv8, EasyOCR, scikit-learn для цветового анализа в CIE Lab
- **Frontend:** Streamlit

Мультимодальная классификационная модель объединяет текстовый эмбеддинг BERT,
визуальный эмбеддинг CLIP и агрегированный вектор детекций YOLO, сливает их
поздним слиянием и подаёт в двухслойный классификатор. Обучаемы только
проекторы и голова, энкодеры заморожены. На валидации достигается точность
около 0.95 на 20 классах.

# Как запустить проект локально?

## Клонирование проекта

В PyCharm: File → Project from Version Control, вставить URL репозитория,
указать папку (по умолчанию `~/PycharmProjects`), нажать Clone. PyCharm сам
откроет проект.

Если удобнее из терминала:

```bash
cd ~/PycharmProjects
git clone <URL репозитория>
cd classification-of-advertising_creatives
```

## Файл .env

В корне проекта должен лежать файл `.env`. В репозитории его нет (он в
`.gitignore`), поэтому при первом запуске его нужно создать вручную. Внутри
просто скопируйте:

```
POSTGRES_USER=user
POSTGRES_PASSWORD=password
POSTGRES_DB=creatives_db
DATABASE_URL=postgresql://user:password@db:5432/creatives_db
TEST_DATABASE_URL=postgresql://user:password@db:5432/test_db
REDIS_URL=redis://redis:6379/0
UPLOAD_FOLDER=./uploads
BACKEND_URL=http://backend:8000
MINIO_ENDPOINT=http://minio:9000
MINIO_ACCESS_KEY=minioadmin
MINIO_SECRET_KEY=minioadmin
MINIO_SECURE=False
MINIO_BUCKET=creatives
MINIO_PUBLIC_URL=http://localhost:9000
CELERY_CONCURRENCY=2

MODEL_CACHE_DIR=/app/models
MODEL_MINIO_BUCKET=models
YOLO_MODEL_PATH=yolov8m.pt
EASYOCR_WEIGHTS_DIR=easy_ocr
BERT_MODEL_PATH=best_multimodal_bert.pt
DEVICE=cpu
```

Значения здесь рассчитаны на локальную разработку, менять их не нужно.

## Загрузка весов моделей

Обученная мультимодальная модель, веса YOLOv8 и веса EasyOCR занимают в сумме
около 600 МБ, поэтому в git их держать неудобно и они исключены через
`.gitignore`. Распространяются отдельно архивом.

Скачайте архив `model.zip`

Положите архив в корень проекта и распакуйте его в папку `minio_init`:

```bash
unzip model.zip -d minio_init/
```

После распаковки в `minio_init/models/` должны оказаться:

```
minio_init/models/
    best_multimodal_bert.pt
    yolov8m.pt
    easy_ocr/
```

Если структура внутри `model.zip` другая (например, файлы лежат прямо в корне
архива, без папки `models`), распакуйте его во временное место и вручную
переместите содержимое в `minio_init/models/` так, чтобы путь получился
именно таким. Сам архив после распаковки можно удалить.

При первом запуске docker-compose эти файлы будут автоматически залиты в
MinIO в бакет `models`, а celery-воркер при старте скачает их себе в volume
`model_cache` и дальше использует оттуда.

## Запуск

Из корня проекта:

```bash
docker compose up -d --build
```

Первый запуск занимает заметное время: Docker должен собрать образы бэкенда,
воркера и фронтенда (скачать torch, transformers, easyocr и другие зависимости)
и один раз прогреть MinIO. Это минут 5–10 в зависимости от канала. Все
последующие запуски — секунды.

После того как всё поднялось, посмотреть статус сервисов:

```bash
docker compose ps
```

Шесть сервисов должны быть в состоянии running или healthy. Сервис
`minio_init` — одноразовый, он делает свою работу (создаёт бакеты и заливает
модели) и корректно завершается с кодом 0, это нормально.

## Доступ к интерфейсам

После успешного запуска:

- http://localhost:8501 — Streamlit-фронтенд, основной интерфейс для
  загрузки и анализа креативов.
- http://localhost:8000/docs — автоматическая Swagger-документация REST API
  бэкенда.
- http://localhost:9001 — консоль MinIO (логин и пароль: `minioadmin` /
  `minioadmin`).
- localhost:5432 — PostgreSQL, если нужно посмотреть базу через DataGrip или
  IDEA (user / password / creatives_db).

## Проверка работоспособности

Откройте фронтенд на http://localhost:8501, создайте группу, загрузите в неё
любое рекламное изображение и подождите несколько секунд. На странице
детального просмотра креатива должны появиться: распознанный текст в зелёных
рамках, найденные объекты в жёлтых рамках, диаграмма распределения цветов и
предсказанная тематика с уверенностью.

Если где-то что-то не открывается или зависает — обычно это видно в логах
воркера:

```bash
docker compose logs -f celery_worker
```

## Полезные команды

Всё запускается из корня проекта.

Остановить всё, сохранив данные:

```bash
docker compose stop
```

Снова запустить:

```bash
docker compose start
```

Смотреть логи одного конкретного сервиса (чаще всего нужны логи воркера):

```bash
docker compose logs -f celery_worker
docker compose logs -f backend
docker compose logs -f frontend
```

Перезапустить один сервис после правки кода:

```bash
docker compose restart backend
```

Полная пересборка образов (нужна, если изменился `requirements.txt` или
Dockerfile):

```bash
docker compose up -d --build
```

Полностью убрать контейнеры (volumes при этом сохраняются):

```bash
docker compose down
```

Сбросить всё под ноль, включая базу, MinIO и кеш моделей, — если хочется
начать с чистого состояния:

```bash
docker compose down -v
```

## Быстрая правка кода без полной пересборки

Контейнеры собираются не с live-reload, поэтому если вы правите, например,
`backend/services/processing_service.py` и хотите увидеть изменения, не
пересобирая образ целиком, можно скопировать файл внутрь контейнера и
перезапустить сервис:

```bash
docker compose cp backend/services/processing_service.py celery_worker:/app/services/processing_service.py
docker compose restart celery_worker
```

Это же работает для `backend/`, только контейнер — `backend`, и для
`frontend/` — контейнер `frontend`. Важно: в контейнере пути начинаются
прямо с `/app/`, без префикса `backend/`.

Такой способ удобен во время разработки и отладки. Когда изменений накопилось
много — лучше один раз пересобрать через `docker compose up -d --build`.

## Типовые проблемы

**Порт уже занят.** При старте docker пишет что-то вроде `port is already
allocated`. Значит один из портов 5432, 6379, 8000, 8501, 9000 или 9001 занят
другим процессом. Посмотреть кем занят порт: `lsof -i :8000`. Обычно это
локально поднятый PostgreSQL или предыдущий контейнер, которого забыли
остановить.

**Воркер падает с ошибкой про отсутствующие веса моделей.** Это значит, что
`minio_init` не смог залить веса в MinIO — скорее всего, потому что папка
`minio_init/models/` пуста (не распакован архив, см. раздел «Загрузка весов
моделей»). Положите веса, затем перезапустите инициализацию и воркер:

```bash
docker compose restart minio_init celery_worker
```

**На странице деталей не показывается картинка.** Проверьте, что контейнеры
`frontend` и `backend` работают, и перезапустите их:

```bash
docker compose restart frontend backend
```

Это локальная особенность, связанная с тем, что MinIO раздаёт файлы по двум
разным адресам — внутреннему (для воркера) и публичному (для браузера).

**После правки кода в контейнере всё по-старому.** Hot-reload не настроен,
нужно либо сделать `docker compose cp` + `restart` конкретного сервиса (см.
раздел выше), либо полностью пересобрать через `docker compose up -d --build`.

## Как устроен проект внутри

Короткая схема того, что происходит, когда пользователь загружает креатив:

```
[пользователь в браузере]
        |
        v
[frontend (Streamlit)]    --->    [backend (FastAPI)]
                                         |
                                         |  кладёт задачу в очередь
                                         v
                                   [redis (брокер)]
                                         |
                                         v
                                [celery_worker]
                                         |
                  +----------+-----------+-----------+------------+
                  |          |           |           |            |
                скачивает    EasyOCR    YOLOv8     K-Means       CLIP
                из MinIO                          в Lab + Delta E  |
                                                                   v
                                                          BERT + CLIP + YOLO
                                                              классификатор
                                                                   |
                                                                   v
                                                   результат записывается
                                                   в PostgreSQL, фронтенд
                                                   показывает его на странице
                                                   деталей креатива
```

PostgreSQL хранит метаданные креативов, группы, пользовательские настройки и
результаты всех этапов анализа. MinIO хранит исходные изображения и веса
моделей. Backend не делает тяжёлую ML-обработку самостоятельно — его задача
только принять файл, положить его в хранилище и поставить задачу в очередь.
Всю обработку делает отдельный celery-воркер; за счёт этого API остаётся
отзывчивым даже при загрузке большой пачки изображений.
